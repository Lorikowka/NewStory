# Проверка первого игрового сценария

Сначала в корне проекта выполните `gradlew.bat build` на Java 17, затем `gradlew.bat runClient`. Для dedicated server используйте `gradlew.bat runServer` после самостоятельного принятия EULA. Эти команды требуют загрузки зависимостей из сети.

В тестовом мире с разрешёнными командами:

1. `/story list` — показывает demo:temple.
2. `/story validate` — показывает VALID и hash встроенной истории.
3. `/story start` — запускает историю для текущего игрока. Появляется заголовок и первая реплика.
4. `/story inspect` — состояние WAITING, waitingEvent=demo:enter_temple.
5. `/story signal demo:enter_temple` — продолжает историю; через 20 серверных тиков появляется финальная реплика.
6. `/story inspect` — состояние COMPLETED.
7. Повторный start создаёт новое прохождение. `/story stop` отменяет текущее; повторная отмена безопасна.
8. Выход, смерть и смена измерения отменяют историю игрока.

Все команды требуют уровня доступа 2. Signal адресуется только истории самого игрока. Это временный администраторский триггер для проверки bridge; автоматическое обнаружение области ещё не реализовано.

Первый JSON-сценарий уже проверен в одиночном мире (см. `STATUS.md`); остальные шаги остаются протоколом ручной приёмки. Камерный renderer, dialogue UI и сохранения ещё не подключены; CameraTrack и ResourceLeases проверяются отдельно как headless-компоненты.

## Проверка Kotlin-сценария

После новой сборки откройте мир с разрешёнными командами. В `run/storyengine/scripts/` должен появиться `chapter_01.se.kts`; существующий файл не перезаписывается. Выполните `/story list`, `/story validate local:chapter_01`, `/story start local:chapter_01`. Появляются две реплики Орена с паузой около двух секунд. Имя и скобки должны быть зелёными, двоеточие и текст — белыми. `run/storyengine/assets/heads/oren.png` заменяет стандартную голову, если положить файл туда до следующего запуска реплики. `/story inspect` после финала показывает COMPLETED. Это новая ручная проверка, она ещё не отмечена выполненной.

## Приёмка reload и взаимодействия

1. Положить samples/kotlin/interaction.se.kts в каталог storyengine/scripts. Выполнить /story reload, дождаться успешного ответа, запустить /story start local:interaction.
2. Проверить WAITING через /story inspect; нажать правой кнопкой основной рукой по блоку. Проверить финальную реплику и COMPLETED.
3. Запустить историю снова и изменить её финальную реплику в файле. Выполнить reload во время ожидания. Текущее прохождение должно показать прежнюю реплику; следующее — новую.
4. Внести синтаксическую ошибку, выполнить reload. Команда должна сообщить об отказе, а start — продолжить запускать прежнюю рабочую версию.
5. Удалить тестовый файл и успешно выполнить reload. История исчезает из list, но уже запущенное прохождение сохраняется.
6. Проверить, что клик второго игрока не продолжает историю первого. Отменённые взаимодействия и вторая рука не должны создавать событие.

Этот сценарий ещё требует ручной игровой приёмки. Headless-тесты отдельно проверяют адресацию, сохранение графов и откат каталога при ошибках.

## Режимы SAY / THOUGHT / WHISPER

Скопировать samples/kotlin/dialogue_modes.se.kts в storyengine/scripts, выполнить /story reload и /story start local:dialogue_modes. Орен должен говорить зелёным именем; его мысль отображается в круглых скобках. Имя Миры голубое, перед её текстом стоит пометка «(шёпотом)». Двоеточие, пометки и текст остаются белыми. Проверить fallback и собственные oren.png/mira.png, остановку и очистку плашки. Визуальная приёмка пока не выполнена.

Проверка текущего файла: после успешной загрузки внесите ошибку в chapter_01.se.kts и выполните /story validate local:chapter_01. Должна прийти ошибка текущего файла, а /story start local:chapter_01 продолжает использовать прежний рабочий граф. После исправления validate показывает новый hash, но только reload активирует его.
