# План реализации Story Engine

## Основание и принятые границы

План сверен с `SPEC.md` и исходным DOCX v1.0, `story_engine_scripting_spec_v0_2.docx`, `ARCHITECTURE.md`, `STATUS.md`, ADR-0001/0002, заметками о чате, игровым протоколом проверки, стилем кода и changelog. Актуальное пожелание владельца: привычная структура Forge MDK; документы в `docs/`; пользовательские сценарии и головы в `gameDir/storyengine/`; сюжетная плашка внизу по центру.

Базовый JSON-граф из v1.0 остаётся действующим форматом определения и проверочным примером. **Решение владельца: пользовательские сценарии пишутся на Kotlin.** Новый документ v0.2 задаёт авторский интерфейс: файл `.se.kts` без обязательной `story {}`-обёртки → типизированный DSL → тот же immutable Story Graph → существующий runtime. JSON-компилятор сохраняется для совместимости, диагностики и будущих Story Pack. Политика доверия к Kotlin и правила импорта остаются открытыми решениями; до запуска стороннего кода их нужно зафиксировать. Kotlin-файлы считать доверенным локальным кодом, пока не появится изоляция; не выдавать их за безопасные пакеты данных. [Официальная документация Kotlin](https://github.com/JetBrains/kotlin-web-site/blob/master/docs/topics/scripting/custom-script-deps-tutorial.md) помечает custom scripting как experimental, поэтому host изолируется в модуле и версии зависимостей фиксируются.

## Текущее состояние — 2 ноября 2026

- **Реализовано и проверено автоматическими тестами:** независимый runtime, JSON-компилятор, Kotlin host, локальные сценарии, ожидания событий, фоновая reload с откатом каталога при ошибке и сохранением активных графов. Выпускной JAR включает внутренние модули и зависимости Kotlin.
- **Реализовано и проверено автоматическими тестами:** say/think/whisper, передача режима реплики клиенту, пример двух персонажей; проверка текущего Kotlin-файла без активации. Режимы портретов CUSTOM_TEXTURE/NONE/FALLBACK проверены автоматическими тестами и компиляцией примера из выпускного JAR.
- **Реализовано, нужна игровая приёмка:** overlay, engine:block_interact, reload внутри мира. Прежний JSON-сценарий подтверждён пользователем; новый клиент прошёл загрузку Forge и текстур, но автоматический захват окна недоступен. Dedicated server остановился на непринятой EULA.
- **Остаётся:** аудитория и участники, manifest Story Pack, портреты AUTO_RENDER, игровая камера, dialogue gate/choice, snapshots, release gate. CI уже настроен; результат удалённого запуска проверяется после push.
## Этапы и критерии приёмки

### 0. DSL и контракт графа — в работе

Ввести независимый от Minecraft `engine-script-api`: `StoryNPC` с id, именем, цветом и portrait id; builder с `say`, `think`, `whisper`, `wait`; устойчивые идентификаторы узлов. Файл верхнего уровня `.se.kts` должен собирать `npc<Oren>().say → wait(2.seconds) → say` без `story(...)`. Kotlin host держать в отдельном модуле, чтобы core не зависел от компилятора. Проверить headless-компиляцию, порядок действий, ошибки файла/строки и отсутствие блокировки. Сначала сделать Java-контракт и тест; затем подключить host и пример файла.

### 1. StoryNPC и реплики — в работе

Заменить захардкоженный `Narrator` типизированными метаданными спикера и режимом SAY/THOUGHT/WHISPER. Передавать имя, цвет, portrait id и аудиторию сервер→клиент; валидировать вход и лимиты пакета. Головы брать из `storyengine/assets/heads/`, при отсутствии — fallback. Проверка: два персонажа с разными цветами, белые двоеточие/текст, корректные скобки и иконки; физическая Entity не требуется.

### 2. Forge bridge и проект сценария

Обнаруживать сценарии в `gameDir/storyengine/scripts/`, компилировать/валидировать до активации, сохранять старую рабочую версию при ошибке. Команды list/validate/start/inspect/stop должны показывать источник и диагностику. Добавить реальные игровые события вместо одного ручного signal, проверку прав и dedicated-server smoke. Hot reload применяется только к новым экземплярам.

### 3. Портреты

Поддержать CUSTOM_TEXTURE, NONE, FALLBACK; затем AUTO_RENDER для модели на клиенте. Запекать геометрию групп головы, не предполагать один UV-прямоугольник. Кэшировать по хешам модели/текстуры/настроек; освобождать GPU-ресурсы. Проверить стандартный скин, многослойную модель и отсутствие GPU на сервере.

### 4. Cinematics MVP

Подключить SceneClock, клиентскую интерполяцию камеры, cue/gate, звук и dialogue UI к серверному графу. Добавить skip/cancel, leases камеры/ввода/NPC и гарантированное восстановление на смерть, выход, смену измерения и ошибку. Проверить полную сцену «Заброшенный храм», в том числе без повторной выдачи cue.

### 5. Persistence

Версионированный snapshot: graph hash, node/fiber state, waits, variables, participants и checkpoint. Писать атомарно, отклонять несовместимую версию, безопасно обрабатывать повреждение. После перезапуска продолжать с контрольной точки без повторного внешнего эффекта; проверить cancel/reconnect.

### 6. Story Pack, инструменты и выпуск MVP

Довести manifest, namespace-ссылки, ресурсы, capabilities, ограничения и диагностику компилятора; сохранить CLI и пример. Добавить trace и тесты отказов, CI, чистую сборку JAR и проверку client + dedicated server. Выпускать MVP лишь после полного сквозного сценария, документации установки/авторства и воспроизводимого release build.

## После MVP

Внутриигровая IDE, визуальный редактор, миграция активных историй, сложные кооперативные ветки и расширенная NPC-анимация. Оба редактора должны строить тот же граф. Их прототипы не блокируют этапы 0–6.

## Порядок проверки

Для каждого этапа: небольшой пример, автоматический headless-тест, затем нужный игровой smoke. На этом компьютере локальный `javac` иногда выдаёт `AccessDeniedException` при закрытии внешнего JAR; успешную компиляцию исходников не считать заменой `scripts/build.cmd` и игровой проверки. Обновлять `STATUS.md` только по фактически проверенным результатам.
